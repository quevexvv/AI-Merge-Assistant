# Вход, статическое качество и экспорт

Реализовал подготовку входа, статическую проверку и экспорт по `team-guide.md`.
Использовал принятые в `dev` DTO версии `1` из `app.services.llm`. Добавил код
и тесты без комментариев; общие API/БД, очередь, runner и GitHub-модуль не менял.

## Установка и проверка

Из корня репозитория, Python 3.13:

```sh
python3.13 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-input-dev.txt
PYTHONPATH=backend .venv/bin/python -m pytest backend/tests/input_quality -q
.venv/bin/ruff check --config backend/ruff-input.toml backend/app/services/parsing backend/app/services/validation backend/app/services/export backend/tests/input_quality
.venv/bin/ruff format --check --config backend/ruff-input.toml backend/app/services/parsing backend/app/services/validation backend/app/services/export backend/tests/input_quality
```

Runtime-зависимости находятся в `backend/requirements-input.txt`; файл зависимостей
LLM не изменён. SDK Gemini для этих проверок не нужен. Все тесты offline. Отдельные
конфигурации Ruff и coverage относятся только к этой зоне; подключение общего CI
остаётся у Макса. Подготовленные тесты не требуют БД, Redis, Docker и ключей.

```sh
PYTHONPATH=backend .venv/bin/python -m coverage run --rcfile=backend/coverage-input.ini -m pytest backend/tests/input_quality -q
.venv/bin/python -m coverage combine --rcfile=backend/coverage-input.ini
.venv/bin/python -m coverage report --rcfile=backend/coverage-input.ini
```

Процессы извлечения получают очищенное окружение, поэтому coverage-инструментация
не внедряется в них. Их результат проверяется через публичный API; отдельные тесты
сверяют прямой контракт парсера с изолированным результатом. Покрытие этих модулей
не является покрытием пользовательского проекта и не даёт допуска к мержу.

## Вызов из оркестратора

```python
from app.services.llm.contracts import EnvironmentProfile
from app.services.parsing import ContextBuilder, SourceFile, extract_document
from app.services.validation import QualityGate
from app.services.export import ExportService

requirements = extract_document("requirements.md", b"Double every integer.")
prepared = ContextBuilder().build(
    run_id="demo-run",
    snapshot_id="demo-snapshot",
    files=(SourceFile("calculator.py", "def double(value):\n    return value * 2\n"),),
    documents=(requirements,),
    environment=EnvironmentProfile(
        profile_id="python-pytest", python_version="3.13", dependencies=("pytest",)
    ),
)
context = prepared.context
scenarios = llm.generate_scenarios(context, budget=scenario_budget)
bundle = llm.generate_tests(context, scenarios, budget=test_budget)
result = QualityGate().validate(context, scenarios, bundle)
if result.passed:
    artifact = ExportService().build(context, scenarios, bundle, format="zip")
else:
    feedback = result.feedback(iteration=1)
```

`llm` и актуальные бюджеты предоставляет оркестратор. `result.passed` означает
только прохождение статического шлюза. Следующий этап — sandbox collect/test.
Ни генерация, ни экспорт не подтверждают корректность поведения или покрытие.

### Документы

`extract_document(path, bytes, limits)` возвращает `DocumentText`: путь, текст,
число страниц PDF либо `None`. MD — UTF-8 с необязательным BOM. DOCX сохраняет
порядок абзацев и текста таблиц основного документа, табуляции и переносы строк.
Внешние связи, вложенные объекты, макросы и OCR не поддерживаются. DOCX не имеет
надёжного числа отображаемых страниц без движка вёрстки; оно не выдумывается.
PDF должен содержать текст; зашифрованный и полностью сканированный PDF отклоняется.

Обработку **всех** документов вызывают в фоновом этапе `preparing`, после регистрации
Run и ответа HTTP 202. Поэтому PDF свыше 50 страниц не удерживает HTTP-запрос.
В модуле нет собственной Celery-очереди и нет дублирования оркестратора. На API
остаются ограничение тела запроса до чтения в память, авторизация и сохранение входа.

PDF/DOCX разбираются отдельным фиксированным Python-процессом без shell, без ключей
из окружения и без импорта пользовательских модулей. Он работает и из daemon-task
worker. При таймауте процесс завершается и ожидается его остановка; на Linux
применяются лимиты CPU и адресного пространства. Это ограничение ресурсов парсера,
а не замена gVisor. Worker-контейнер также должен иметь общие лимиты и ограниченный
доступ к сети и файловой системе.

### Python и ZIP

`SourceFile` принимает точный относительный путь и текст. `read_code_archive(bytes)`
читает только Python-файлы в память и не распаковывает их на диск. Другие файлы,
небезопасные пути, повторяющиеся имена с учётом регистра, symlink, encrypted ZIP,
коллизии файл/каталог и превышение лимитов отклоняются. Пути должны быть POSIX/NFC;
абсолютные пути, `..`, обратные слеши, управляющие символы, Windows device names,
`.git` и неоднозначные платформенные формы не допускаются.

`analyze_code` использует AST Python 3.13, не импортирует и не запускает код.
Возвращает функции/классы верхнего уровня и один непрерывный фрагмент с исходным
`start_line`, включающий затронутые определения, декораторы, выражения верхнего
уровня и транзитивно используемые функции/классы этого модуля. Зависимости выбираются
консервативно по AST-именам; совпадение с локальным именем может расширить контекст.
Динамическое разрешение имён не выполняется. Несколько далёких изменений могут
расширить фрагмент; текст и окончания строк внутри него не переписываются.
Лимиты не приводят к молчаливому обрезанию требований или изменённого кода.

### GitHub и измеряемые строки

Для GitHub передают `GitHubInput(repository_id, source_sha, target_sha, diff)`.
Принимается обычный unified diff, включая добавление, удаление и rename. Binary,
combined diff и неоднозначные quoted paths отклоняются. Заголовки, счётчики hunks
и новые/context-строки сверяются с предоставленным содержимым. Перекрывающиеся
hunks отклоняются на обеих сторонах diff. Снимок после удаления всех Python-файлов
может быть пустым; пустая загрузка без GitHub отклоняется. Происхождение
полного снимка, полнота diff и соответствие SHA проверяются GitHub-модулем.

Snapshot hash — SHA-256 канонического набора точных путей/содержимого и diff;
порядок файлов его не меняет. Snapshot ID нельзя переиспользовать для другого
содержимого. Текст требований и профиль сохраняются вместе с конкретным Run.
Прикладные файлы и существующие тесты автоматически защищены от записи генератора.
Каталог сгенерированных тестов должен быть свободен в исходном снимке.

`PreparedInput.changes` содержит **текстовые** добавленные строки;
`measurement_paths` задаёт прикладные пути для измерения. В upload это весь
прикладной Python-код, включая пустые файлы; для GitHub — изменённые существующие
прикладные пути. Тесты не включаются. Удалённые файлы остаются в `changes`.

`GenerationContext.changed_lines` намеренно не заполняется текстовыми строками.
По договору именно Артём З сопоставляет их с исполняемыми строками отчёта runner
окончательного кандидата. Перед coverage-feedback он добавляет измеренные строки
и, при необходимости, полный исходник вместо сокращённого фрагмента. Ни AST,
ни добавленная строка сами по себе не доказывают исполняемость.

Default требует явные требования/описание, а upload — документ требований и
default. Lazy доступен со снимком GitHub; его сценарии имеют `inferred`.
Неизменённые code/existing_test помечаются optional для уже существующего LLM
бюджетирования. Изменённые файлы, требования и diff обязательны.

## Статический шлюз

`QualityGate.validate(context, scenarios, bundle)` повторно проверяет схемы и хеш,
принадлежность run/snapshot, допустимые пути, источники сценариев, происхождение
ожиданий, связь каждого сценария с тестами, синтаксис Python и Gherkin.
В default каждый сценарий должен ссылаться хотя бы на источник требований или
описания; это проверка происхождения, а не семантическое доказательство требования.

Политика первой версии сознательно ограничена простыми pytest-тестами:

- Файлы `test_*.py` внутри разрешённого каталога; хотя бы один тест с assert или
  pytest.raises. Константный assert, отсутствующий тест и синтаксическая ошибка
  отклоняются. Вложенная невызываемая функция не считается assertion теста.
- Импорты pytest, небольшого разрешённого набора стандартных модулей и модулей
  приложения. Дополнительные import roots задаёт сервер через `StaticPolicy`;
  название pip-дистрибутива автоматически не превращается в разрешение импорта.
- Запрет прямых системных/сетевых импортов, exec/eval/open, динамического доступа,
  pytest hooks/plugins, skip/xfail, исключений coverage и очевидных изменений
  чужих объектов. Проверяются алиасы импортов, декораторы, defaults и вызовы
  в аннотациях. Параметризация принимает literal-значения, разрешены pytest.fixture
  и простые Test-классы.

Шлюз отклоняет assertions, состоящие только из констант и операций над ними,
перехват `AssertionError`/`Exception`/`BaseException`, bare except и выход из finally
через return/break/continue. Для ожидаемых исключений используется `pytest.raises`.

Статический анализ не может доказать безопасность Python или силу утверждений.
Косвенные вызовы, импортируемый прикладной код, сложные fixture и семантика тестов
проверяются дальше в sandbox и человеком. Даже прошедшие файлы нельзя импортировать
в API/LLM-worker. Ни pytest collection, ни запуск subprocess с пользовательским
кодом внутри этих модулей не выполняются.

При обычном отказе возвращается bounded-список `ValidationIssue`; `feedback(1)`
создаёт существующий DTO `ValidationFeedback` с `validation_error` и точным хешем.
Неверные ID/хеш/схема или превышение размеров дают `InputError`, а не feedback
для другого снимка. Ошибки содержат фиксированный код без исходника/текста parser
exception. Не логируйте полные DTO, входы, `model_dump` или содержимое экспортов.

## Экспорт и хранение

`ExportService.build(..., format="feature" | "py" | "zip", path=...)` всегда
повторно выполняет шлюз. Для нескольких Python-файлов требуется точный `path`
из bundle. Возвращает `ExportArtifact(filename, media_type, content)` со свойствами
`size` и `sha256`. Имена для HTTP выдачи не берутся из run ID или произвольного ввода.

ZIP детерминирован: сортировка записей, фиксированное время, обычные файлы 0644.
Он содержит только проверенные тесты, `scenarios.feature` и `manifest.json` с
хешами, происхождением ожиданий, связями источников и отметкой `static_only`.
Пользовательские исходники, документы, ключи и пути хранилища туда не включаются.
Экспорт создаётся в памяти и не открывает файловые пути модели: traversal/symlink
при записи исключаются отсутствием такой записи. Артём З сохраняет bytes под
серверным ID в volume, фиксирует владельца/размер/хеш/срок хранения и проверяет
принадлежность при скачивании. HTTP-выдача требует attachment и nosniff.

## Начальные лимиты

| Ограничение | Значение |
|---|---:|
| Документ / сжатый ZIP | 10 MB |
| Суммарный распакованный ZIP | 30 MB |
| Записи ZIP / степень сжатия | 500 / 100:1 |
| PDF | 500 страниц |
| Извлечённый текст | 1 000 000 символов |
| Python-файл / количество | 500 KB / 200 |
| Полный исходник / подготовленный контекст | 5 MB |
| AST | 50 000 узлов на файл |
| Парсер документа | 15 секунд / 512 MiB адресного пространства на Linux |
| Сгенерированные файлы / их суммарный размер | 100 / 2 MB |
| Сценарии / issues | 200 / 100 |

Это настройки приложения, не согласованные квоты VPS. Макс и Артём З могут
уменьшить их серверной конфигурацией. Параллельность документов ограничивает
очередь; пользователь не управляет лимитами через HTTP.

## Передача команде

В `feature/backend_API` на момент реализации имеется другой контракт `T1`
(`source_snapshot`, `code_fragments`, UUID), ещё не принятый в `dev`. Его нельзя
выдать за совместимый с существующим LLM-контрактом `1`. Изменения общих схем
согласует Артём З с потребителями отдельным PR. В этой реализации второй набор
общих DTO не создаётся и чужие схемы не переписываются.

Артём З подключает вызовы к preparing/validating/export, хранение и авторизацию;
Макс подключает зависимости и команды проверки к worker/CI, подтверждает профиль
окружения и лимиты. Вадим получает готовый GenerationContext и статический feedback.
Реальный LLM, gVisor, coverage пользовательского проекта и демонстрация заданного
дефекта должны быть проверены общей вертикалью I1/I2; offline fake этого не заменяет.

Fixtures ошибок находятся в параметризованных тестах `backend/tests/input_quality`:
повреждённый документ, XML entity, опасные ZIP-пути, bomb/symlink/коллизии, неверный
diff/снимок, синтаксис, подмена хеша, suppress-тесты, Gherkin injection, запрещённый
экспорт. Общие context/scenarios/bundle fixtures — в `conftest.py`.
